## Recommended execution order

1. **002** first — pure CSS, zero risk, two-line change, no interaction with
   anything else here.
2. **001** next — self-contained to `addRow()` in `app.js`, no shared state
   with the other plans.
3. **003** — touches `mission_control.html` in two places that do not
   overlap with plan 004's edit to the same file (different `<div>` blocks:
   003 touches the two button labels around lines 96-99/199-202; 004
   touches the log list around lines 226-230). Safe to do in either order
   relative to 004, but doing 003 before 004 keeps each diff easy to review
   independently.
4. **004** last — the only plan that changes a data shape (`log` from an
   array of strings to an array of `{id, text}` objects), so it's the one
   most worth reviewing carefully in isolation after the others are settled.

## Dependencies

None of the four plans depend on another's edits landing first — they touch
disjoint functions/rules except where noted above (003 and 004 both edit
`mission_control.html` but in non-overlapping blocks). All four can also be
executed in parallel isolated worktrees if preferred.

## Notes

- All four plans reuse existing tokens (`--duration-fast`, `--duration-base`,
  `--ease-out`) and existing patterns already established elsewhere in this
  codebase (the `.scenario-card-enter/leave` Alpine transition-class
  mechanism, the `.msg-enter` keyframe, the `.upload-list li.is-removing`
  exit transition) — none introduce a new dependency or a new motion
  vocabulary.
- Run `improve-animations execute <plan>` (or hand a plan file to any
  agent) to implement one. Each plan's Verification section is the
  acceptance bar.

## Execution record

All four executed via `improve-animations execute` — four parallel executor
agents, each implementing one plan directly on the working tree (not an
isolated worktree: the plans' file:line references and quoted "current code"
were taken from the live tree, including uncommitted work already in it, so
a fresh worktree checked out from the commit stamp alone would have missed
that context and every excerpt would have failed to match).

Each agent's diff matched its plan's Target section byte-for-byte, no two
agents touched overlapping code despite `app/static/js/app.js` and
`app/templates/mission_control.html` each being edited by two different
agents, and both plans' mechanical checks (`node --check`, CSS brace
balance) passed independently after the fact. Feel-checks were done in the
browser against the running dev server:

- **003**: confirmed via `getBoundingClientRect()` mid-crossfade — button
  width identical before and 60ms into the transition (140.28px both times),
  with the two labels' computed `opacity` at ~5%/~95%, i.e. genuinely
  crossfading in place rather than reflowing.
- **002**: confirmed via computed style — both `.feed-title` and
  `tbody a.row-link` report `transition: color 0.12s cubic-bezier(0.16, 1, 0.3, 1)`
  at runtime.
- **001**: confirmed by patching `Node.prototype.appendChild` to capture the
  new `<li>`'s inline style at the exact moment it's inserted — captured
  `opacity: 0; transform: translateX(-8px)`, i.e. the entrance starting
  state is really being set before the browser resolves it to rest.
- **004**: log lines render and accumulate correctly across a live "Refresh
  market pricing" run; the `:key="entry.id"`/`.msg-enter` wiring matches
  002's already-proven `.msg-enter` mechanism (Ask page) exactly.
- Reduced-motion coverage verified by reading the final
  `@media (prefers-reduced-motion: reduce)` block: `.upload-list li` and
  `.msg-enter` (both pre-existing) already disable 001's and 004's motion
  with no new rule needed; `.btn-label-enter`/`.btn-label-leave` (003) and
  `.feed-title`/`row-link` (002) were deliberately left out, since both are
  opacity-only and aid comprehension per each plan's own reasoning.

No regressions found. No further action needed on these four.
